# AEGIS Research Dataset Specification

**Project:** AEGIS — Experience-Driven Autonomous Intelligence Platform
**Dataset:** AEGIS Agent Task Benchmark
**Initial version:** 0.1.0
**Status:** Specification — dataset collection has not started

---

## 1. Purpose

The AEGIS Agent Task Benchmark will provide a reproducible evaluation environment for investigating whether persistent experience, structured memory, and feedback-driven strategy adaptation improve autonomous agent performance.

The dataset must support controlled comparisons between different agent configurations.

It must not be treated as evidence of autonomous intelligence merely because it contains a large number of examples.

## 2. Dataset Scope

The planned benchmark will cover six task categories:

1. Basic task execution
2. Multi-step planning
3. Memory and information retrieval
4. Tool selection
5. Failure detection and recovery
6. Feedback-driven strategy adaptation

These categories describe the intended research scope. They do not imply that all capabilities are currently implemented in AEGIS.

Each category will be introduced only when its task definitions and evaluation criteria can be implemented and independently verified.

## 3. Dataset Record Schema

Every benchmark case must contain the following fields:

| Field | Description |
|---|---|
| `case_id` | Unique, stable identifier |
| `category` | Research task category |
| `difficulty` | `basic`, `intermediate`, or `advanced` |
| `task` | Instruction presented to the agent |
| `context` | Relevant information available before execution |
| `expected_outcome` | Expected result or final state |
| `success_criteria` | Explicit conditions used to evaluate success |
| `allowed_tools` | Tools permitted for the task |
| `source` | Origin of the example |
| `license` | Applicable source licence or usage terms |
| `group_id` | Identifier linking related or derived cases |
| `validation_status` | `draft`, `reviewed`, or `approved` |

### Data Quality Rules

- Every case must have a unique identifier.
- Required fields cannot be empty.
- Categories and difficulty values must use controlled vocabularies.
- Success criteria must be testable.
- Expected outcomes must not be generated by copying the agent's own output.
- Source and licensing information must be recorded.
- Derived examples must retain their original group identifier.
- Ambiguous or unverified examples must not enter the approved dataset.

## 4. Data Sources

Potential sources include:

- Public datasets with compatible licences.
- Carefully designed human-authored scenarios.
- Programmatically generated scenarios with validation.
- Controlled agent execution and failure-recovery experiments.
- Human-reviewed task examples.

Every imported source must be reviewed for licensing, attribution, suitability, and redistribution restrictions.

Synthetic examples must be identified as synthetic.

## 5. Dataset Lifecycle

The dataset will progress through four stages:

1. **Raw:** Original collected or authored examples.
2. **Processed:** Normalized records with consistent fields.
3. **Validated:** Records that pass schema and quality checks.
4. **Split:** Approved records assigned to training, validation, and testing partitions.

Original source records must remain recoverable.

Changes to the dataset must result in a new version.

## 6. Train, Validation, and Test Strategy

The initial target split is:

- Training: 70%
- Validation: 15%
- Testing: 15%

Splitting must be deterministic and reproducible using a recorded random seed.

Cases sharing a `group_id` must remain in the same partition to prevent related examples from leaking across partitions.

The test partition must remain untouched during model development and hyperparameter selection.

The split percentages are targets. Small datasets may require adjustments, which must be documented.

## 7. Dataset Validation

The validation pipeline must check:

- Schema compliance.
- Unique case identifiers.
- Missing required values.
- Valid category and difficulty values.
- Valid source and licensing metadata.
- Duplicate records.
- Related-case grouping.
- Expected-outcome consistency.
- Success-criteria completeness.
- Split leakage.

Validation failures must produce understandable error messages.

Invalid records must not silently enter the approved dataset.

## 8. Evaluation Principles

AEGIS will compare multiple configurations, including:

- Fixed strategy without persistent memory.
- Random strategy selection.
- Memory-enabled execution.
- Feedback-driven adaptation.
- Combined memory and adaptation.

The exact baselines will depend on which capabilities are implemented and experimentally controlled.

Evaluation should measure:

- Task success rate.
- Planning and execution correctness.
- Tool-selection correctness.
- Memory retrieval precision and recall.
- Failure recovery rate.
- Adaptation improvement.
- Execution latency.
- Generalization to held-out tasks.

Results must include sample sizes and appropriate uncertainty estimates.

## 9. Research Integrity

- Do not invent experimental results.
- Do not describe proposed examples as collected data.
- Do not report training performance as test performance.
- Do not tune against the held-out test set.
- Record dataset versions and experiment configurations.
- Report limitations and negative results honestly.
- Keep the existing five-case text-analysis benchmark separate from the new agent-task research dataset.

## 10. Initial Development Target

The first implementation milestone is a small, carefully validated dataset pipeline.

It must support:

1. Loading structured JSONL records.
2. Validating records against the schema.
3. Detecting duplicate identifiers.
4. Checking related-case groups.
5. Producing reproducible leakage-free splits.
6. Recording dataset version and validation results.

The proposed target of approximately 6,000 cases is a future research objective, not an existing dataset or a mandatory generation quota.
